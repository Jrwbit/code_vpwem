## 当前搜索的限制

生产调用的CPU走廊搜索使用max_hover_q=1、n_rand=8、extra_hovers=0，悬停距离候选为0.11/0.15/0.08/0.06米。走廊按若干水平方向和坡度向外延伸，走廊内保持工具朝向不变。函数支持更广的候选搜索，但当前调用为了效率收窄了范围。

代码 `swap.raised` 已沿工具/盒体局部Z后退构造悬停点，`scene.targets` 已沿目标局部Z生成最后接近位。因此不能把“需要沿倾斜法向接近”描述成现有代码完全没有做到；更可能需要检查的是合法关节分支、走廊中保持倾斜姿态时的可行性，以及有限方向/高度/肘姿组合的覆盖情况。

“0个走廊候选”只证明本次搜索没有找到满足既定要求的候选，不证明所有关节解和所有通路都不存在。日志中的32个verified GPU seeds也不能单独当作完整合法对位及返回路线已存在的证据。现有日志没有逐类统计终点IK失败、末端碰撞、同分支接近失败、腕部联合限位或走廊中间碰撞，尚不能唯一确定倾斜场景的阻塞项。

## 建议的处理顺序

1. 固定当前新视觉结果，离线对最终对位点、最后接近点和悬停点分别做多初值逆解，并逐一检查真实限位、腕部联合约束及模型碰撞；输出是哪一层无合法候选，不先盲目增加整条搜索时间。
2. 如果终点存在合法解，扩大肘姿分支、悬停距离/高度、走廊侧向及坡度候选，保留最后接近段沿接线盒法向的要求，并对所有实际导出关节线重新检查。
3. 对固定朝向的长走廊仍不可行的情况，考虑增加空旷的中间调姿位，使避障段与最终倾斜对位段分开求解，再检查朝向变化过程；不能直接跳接两个端点或取消连续性检查。
4. 如果最终位姿在当前腰姿和工具下始终无合法关节解，扩大路径搜索未必有用，应检查调整电机位置/倾角/高度或工具安装的可行性。腰部变姿属于另一种规划方案，且现场仍有−514/保持问题，不能作为未经验证的自动兜底。

优先方向是“明确失败约束→扩大分支/走廊搜索→必要时中间调姿”，不重新调整已用的手眼矩阵，不放宽碰撞或软限位，不承诺任意倾角都能执行。完成候选求解后还需完整路径复核与实际执行验证。
