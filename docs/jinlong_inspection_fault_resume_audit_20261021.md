# 运动报错后无法继续检测：现场核对与续检方案（2026-10-21）

## 结论

可以实现故障后的断点续检，但现有完整检测流程仅支持正常检测点暂停后的继续，不支持任意故障退出后直接续接。此次现场最新运动记录显示，触发停止的是非目标部件身体第4轴反馈速度超限，不能作为普通通信瞬断自动清错重试。此次仅作只读排查，没有清警、上电、运动、解除锁存、修改保护参数或部署代码。

## 为什么恢复控制后仍不能继续

控制侧 `helios_hmi/motion.py::recover_control` 在反馈和身份检查通过后解除软件锁存并作废旧预览，明确不续跑原任务。`helios_hmi/plan_runner.py::resume` 仅接受仍active且phase=at_target的正常暂停任务。

检测侧 `robot/rokae_trajectory.py::start_trajectory` 同样只接受ready或正常at_target；执行异常时任务变为failed并请求stop。当前流程没有“从故障实际停点重新建立剩余路线”的恢复入口。现场motion已经idle且未锁存，与plan仍failed可以同时成立。

## 处理路径

1. 先核对身体第4轴的当前故障、静止稳定性及腰姿变化原因。此处不能靠放宽非目标轴速度或漂移门限处理。当前SDK故障信息仍依赖操作端核对，不能把历史报警或空闲反馈当作当前无故障的完整证明。
2. 原因排除、退出状态确认后，以实际停点重新校验连接路径及剩余路线。腰姿变化会影响相机和机器人坐标关系；需要检查原视觉、场景和标定绑定是否仍有效，不满足时重新采图规划。
3. 对本次任务，保留已完成6个关节点的证据；第7点只完成一部分，应从实际停点连接并检查剩余部分，不能跳到第8点，也不能无检查重发整段。若要先回到已完成点，也须检查反向连接路径。
4. 在软件中增加“故障后恢复检测”：保存原计划摘要、实际停止关节、逐点完成记录、工装/场景/标定/控制器运动学绑定及检测结果状态；故障后先确认退出、重新检查绑定和剩余碰撞路径，再生成新的恢复计划及操作身份。保留已证实完成的步骤；到位但没有检测完成回执的步骤不能标记检测完成。
5. 通信类暂时故障只有在能消除命令是否执行的不确定性、确认安全退出、复核实际位置与绑定后，才适合设计有限次数自动恢复。身体意外运动、碰撞、急停及持续控制器报警应等待处理后再恢复。

上述为实现方向，尚未实施或验收故障续检功能；此次也没有执行现场恢复动作。用户尚未提供页面错误文字和发生时刻，故以上以现场最新运动失败记录对应本次现象，若用户指另一条错误需继续对照。
