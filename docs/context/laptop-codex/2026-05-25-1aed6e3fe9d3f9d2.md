而且队列用的是“只保留最新帧”的逻辑，满了会丢旧帧：

```python
_enqueue_latest(...)
```

所以它不是那种相机帧排队越积越多、导致几秒延迟的结构。

从你前一次日志看，瓶颈主要在这里：

```text
camera: avg 0.31ms
vision: avg 8.61ms
action: avg 200.73ms
infer_latency_ms avg=198.16ms
```

也就是说，相机和预处理都很快，真正慢的是 DP 推理，一次约 200ms，实际频率大概 5Hz。

手闭合晚，最可能是这几个原因：

1. **policy 本身晚输出闭手**
   你的日志里之前一直看到：

   ```text
   hand_delta = 0.0
   ```

   说明 policy 当前输出的手部目标和当前 `right_hand=1000` 一样，还是张开状态。它不是没下发，而是没预测到要闭合。

2. **手部输出已经反归一化，但可能一直接近 1.0**
   代码里有：

   ```python
   grip = int(np.clip(action_step0[7], 0.0, 1.0) * 1000.0)
   ```

   所以 `action[7]=1.0` 就是 `1000` 张开，`action[7]=0.0` 才是闭合。

3. **CANFD 下发机械臂是非阻塞，手是在同一 cycle 里随后下发**
   代码顺序是：

   ```python
   rc_arm = rm_movej_canfd(...)
   rc_hand = write_raw_pose(...)
   ```

   所以如果 policy 同一帧已经给了闭手，程序不会等机械臂走完才闭手。你看到“过了电批很久才闭合”，更像是 policy 的手部 action 晚了，或者手本体动作慢。

4. **推理 5Hz 会放大视觉反应延迟**
   即使相机没有排队，policy 每 200ms 才更新一次。如果模型要等看到某个视觉状态才闭手，反应会比 10Hz 目标慢一倍以上。

下一步建议不要猜，直接看每个 cycle 的手部输出。你要关注日志里这两个量：

```text
policy action[7]   # 0-1
grip               # 0-1000
```

如果机械臂已经过了电批，但 `action[7]` 还一直接近 `1.0`，那就是模型策略晚闭手，不是执行链路问题。

如果 `action[7]` 已经降到接近 `0.0`，但真实手很久才闭合，那才是手部 Modbus/灵巧手动作速度问题。
