### 推荐优化顺序

1. 产物异步化或分级保存

在线控制只同步返回数值结果和必要质量指标，完整 RGB、深度、伪彩和中间 mask 放后台线程写入；成功帧可只保存摘要，失败帧保存全量。

直接收益约 `0.9 s`，不改变任何算法结果，是第一优先级。

2. 粗检测降采样，精修恢复全分辨率

粗多平面阶段不需要使用 166 万个深度点。建议采用：

- 像素步长 `2～4`，或 2–3 mm 体素降采样；
- 粗 RANSAC 只在降采样点云上运行；
- 候选 ROI 确定后，再回到原始深度做精平面和边支持验证。

这不会丢掉最终精度，因为最终中心和法向仍使用原始深度。预计可把约 `726 ms` 的粗平面部分压缩到 `150～300 ms`，但需要冻结数据集验证。

3. 最终平面使用“粗平面引导精修”

当前候选点已经经过 ±2 mm 粗平面筛选，之后又调用 [compare_detection_methods.py](/[REDACTED long identifier].py:111) 从零执行 1500 次 RANSAC。

建议改为：

```text
粗平面
→ 回扫原始 ROI 中距粗平面 ±2～3 mm 的点
→ 一次 PCA/SVD
→ 按残差剔除离群点
→ 再做一次 PCA/SVD
```

保留最终精修，但不重新盲搜平面。预计节省 `70～100 ms`。

4. RANSAC 批量化和自适应停止

现在 Python 循环逐个生成假设，每次执行一次 `fit_points @ normal`。可改成：

- 一次生成 32/64 个平面假设；
- 用矩阵运算批量计算所有点到所有平面的距离；
- 根据当前内点率和目标置信度动态计算剩余迭代次数；
- 找到高质量矩形候选后进入验证式提前停止。

这比机械减少固定迭代次数安全。

5. 候选连通域提前过滤

目前很多连通域进入三维投影、`minAreaRect` 和完整 mask 构造。可先用连通域已有的：

- 像素面积；
- 像素包围框长宽比；
- 工作区位置；
- 深度跨度；
- 粗物理尺寸；

做廉价排除，再构造三维矩形。当前该部分约 `124 ms`。

6. 不再对平面点永久硬删除

当前串行 RANSAC 在每个平面完成后立即删除其内点。这不仅影响耗时策略，也是历史 C 形 ROI 的根因：目标边上的点可能先被侧平面抢走。已有实验记录某一帧右边 2010 个有效点中有 1597 个被早期平面消耗，见 [平面ROI多方案对照实验](/home/wjr/code/r435/docs/平面ROI多方案对照实验_20260729.md:111)。

建议保留原始点索引，粗平面只用于提出候选；选出目标平面后，从原始深度重新收集最终平面附近的点。这一步可能增加几十毫秒局部回扫，但能减少错误候选和重复补救，整体更稳。

### 最终建议

不要直接删“多平面”或把参数粗暴降为 `100×4`。推荐的目标结构是：

```text

→ 批量/自适应粗平面候选
→ 廉价尺寸与位置预筛
```

按当前实测，比较现实的优化目标是：纯算法从约 `1.04 s` 降至 `0.35～0.55 s`，在线同步产物从约 `0.9 s` 降至几十毫秒以内；同时保留 6 平面覆盖能力和最终全分辨率精度。这个目标需要用现有正常帧、C 形缺边帧和历史失败帧一起做回放验收，不能只以平均耗时或正常帧通过率决定上线。

网页平时运行的是常驻 RGB 预览流，但执行深度任务时会：

```text
停止 RGB 预览
→ MV3D_RGBD_Stop
→ CloseDevice
→ 深度子进程重新 OpenDevice
→ 配置 RGB-D 对齐并 Start
→ 采集和运行算法
→ 深度进程关闭相机
→ 重新 OpenDevice 恢复 RGB 预览
```

任务入口明确调用了 `camera_runtime.stop()`，见 [hik_web_tasks.py](/[REDACTED long identifier].py:475)。

而 `stop()` 最终会执行 `MV3D_RGBD_Stop()` 和 `MV3D_RGBD_CloseDevice()`，见 [hik_fast_rgb_service.py](/[REDACTED long identifier].py:380)。

因此现在只能说“相机平时有 RGB 预览”，不能说“深度相机一直预热”。每次任务都重新打开设备、重新启用深度和对齐，可能引入：

- 启动等待时间；
- 前几帧深度不稳定；
- 激光器/深度模组温漂；
- 曝光和参数重新生效；
- RGB-D 对齐流重新建立；
- 偶发设备打开或预览恢复失败。

推荐结构

应该把相机改成唯一的常驻 RGB-D 采集进程：

```text
服务启动
→ 相机只 OpenDevice 一次
→ 配置 RGB-D、深度范围和对齐
→ Start 一次
→ 持续采集并丢弃预热阶段帧
→ RGB 帧送网页预览
→ 对齐 RGB-D 帧存入环形缓存
→ 检测任务读取最新稳定帧
→ 算法运行时相机继续采集
→ 服务退出时才 Stop/Close
```

也就是网页预览和深度算法不再分别抢占相机，而是共同消费同一个常驻采集进程的数据。

预热就绪门建议

服务启动后不要立刻允许机器人任务，增加 `camera_ready` 状态。只有以下条件满足才放行：

- RGB-D 流持续运行超过规定预热时间；
- 已连续取得足够数量的完整对齐帧；
- 深度有效率连续合格；
- 固定参考区域的深度中位数和波动连续稳定；
- 帧时间戳单调、帧龄合格；
- 曝光、增益、激光、对齐和深度范围参数读取回验成功；
- 如果 SDK 能读取设备温度，再增加温度变化率门限。

一旦发生以下事件，应把 `camera_ready` 重新置为 `false`：

- `Stop/CloseDevice`；
- USB 断连或重新枚举；
- 连续取帧失败；
- 相机参数或工作模式发生变化；
- 深度有效率或参考区域稳定性持续异常。

预热时间不要凭经验硬写成固定数字，应该现场采集启动后数分钟的“设备温度、参考平面深度中位数、平面法向和有效率”，根据稳定曲线确定。例如最终可能是 30 秒、60 秒或更长，但要由相机实测决定。

1. 先取消任务中的 `camera_runtime.stop()` 和深度子进程重新开相机。
2. 将常驻服务改为持续输出对齐 RGB-D。
3. 增加带时间戳的 RGB-D 环形缓存，算法只取同一帧对。
4. 增加 `warming_up / ready / unstable / disconnected` 状态机。
