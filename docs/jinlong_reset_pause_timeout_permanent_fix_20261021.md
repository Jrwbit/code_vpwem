# 检测到位后复位无法完成：原因、持久修复及现场验证（2026-10-21）

## 交付结果

用户反馈新手眼标定下检测位置已经准确，但“生成复位路线”持续未完成。本轮确认两个返回来源处理缺陷，已修改生产代码、提交并部署到实际检测服务。现场通过原HTTP接口连续两次生成复位路线，分别约8.788秒和8.875秒，均ready、collision_checked=true。当前页面保留第二次生成的复位任务 `a02fd5dd536246e1b9ff76d59fab418a`，绑定原检测路线 `713f4367653746688e422700ad4e34ed`。

本轮没有启动复位运动、上电或清警，没有修改新手眼标定、工位几何、控制器参数、碰撞/限位门限或5分钟检测暂停期限。交付为生产复位入口的持久软件修复及真实规划验证，不宣称控制器硬件故障已解决，也不宣称任意故障停点都能自动续检。

## 问题为何出现

### 1. 已完成检测对位，但暂停超时后原撤离来源被忽略

现场HMI计划 `inspection_713f4367653746688e422700ad4e34ed.json` 前4段完成进度为2/2、5/5、2/2、1/1，后4段返回均未执行；原返回checkpoint保存了同一operation_id、计划摘要、到位进度和归档摘要。任务在检测点保持上电暂停超过5分钟，原生退出报 `route inspection pause timeout`，safe_exit_confirmed=true，当前三部件下电空闲且未锁存。

`rokae_retreat.bound_retreat()` 原逻辑只在HMI没有加载计划时读取持久checkpoint。已加载计划的phase变为failed后，该函数直接返回None，尽管正确的到位记录和原撤离段仍完整存在。

因此失败复位任务 `8e0def3ae70e4a659b252abe75c35f47` 没有retreat_source，转入 `detection_initial_segments → fewest_connect`，尝试从插接位置按普通收臂规则连home，报“连不上（0个中间点从起点可达，2个可到终点）”。这是终态失败，不是规划线程无限运行；并不能证明原撤离路线不可用，也不支持把原因归于新标定。

修复后，failed/stopped任务只有在计划名、摘要、非空operation_id、阶段索引和全部完成进度均与归档绑定的checkpoint一致时，才恢复该检测到位记录，再执行原有工具、标定、视觉、静态部件和路径检查。运行中的任务、已开始返回、换任务、摘要变化、归档损坏仍拒绝恢复。没有降低碰撞规则或以历史任意路线替代当前来源。

### 2. 首次复位可生成，但重复生成时误把腰部修正当成左臂撤离

第一项修复后的现场首次预览已经ready：原4段左臂撤离返回之后，规划器按当前反馈追加约0.12°的腰部工作姿态修正，因此新计划包含5段。重复点击生成时，旧逻辑把这5段都作为原撤离路线处理，遇到waist组时报“原撤离路线阶段无效”。

第二项修复将复位来源限定为原始绑定的左臂撤离前缀；仅允许其后出现腰部恢复段。重新生成时，左臂撤离前缀重新检查，腰部恢复由规划器从当前反馈重新计算。未执行复位可以重复预览；已有执行进度的复位仍拒绝从检测终点重新开始。

## 部署中发现并处理的验证问题

初次部署在生产运行目录执行既有轨迹测试时，其中一个测试没有隔离clear_retreat_checkpoint，误删了现场返回记录。根据部署前受限备份，核对原计划名、摘要、operation_id、阶段及全部进度未变，且归档哈希完全一致后，原样恢复该checkpoint，未编造到位记录。部署工具随后改用临时R435_RELEASE_ROOT；第二轮45项检查后checkpoint与备份逐字节一致。

两次服务重启后的第一次相机模式恢复POST均返回409；源码提交和检测服务已启动，但部署脚本没有完成其最后验证。随后用原存档任务的同一参数单独恢复相机，返回ready，再完成配置、checkpoint、既有diff、锁状态和运行revision的独立回读核对。没有把首次409写成成功，也没有因相机暂时冲突重启HMI或机器人。此启动时相机交接冲突未作为本轮复位逻辑修复的成果。
