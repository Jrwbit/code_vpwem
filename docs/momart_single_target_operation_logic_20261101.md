# MoMaRT 单目标条件：操作逻辑、切换条件与实施边界

2026-11-01。根据现有配置、已完成缓存和单目标选择原型梳理。本文是待验证的操作设计，不是已实现的控制器，也不把代理选框指标当作任务成功率。

## 先纠正目标定义

“当前机器人要接触哪个物体”不足以描述整个任务。抓碗阶段要定位碗，携带碗去放置时要定位目的地；碗仍是被操作物体，但当前需要引导接近的位置可能已变为碗架。混成一个无角色标签，会把正确的阶段变化和错误换目标混在一起。

分别维护：

- 任务目标：物品从哪里转移到哪里，由任务ID及观测确定。
- 当前阶段：准备容器、接近、抓取、搬运、放置、确认或恢复；是状态估计，不是按时间推进的脚本。
- 操作主体subject：例如本次选中的那只碗；搬运中不能因为接收区域更显眼就丢掉主体身份。
- 当前交互目标active_target：当前阶段需要定位的具体对象实例或操作区域。抓取时为碗，放置接近时为接收区域。

选择器内部可以维护多个对象；传给动作模型的对象条件最多一个。一个框是否足够支持控制仍需实验，不能仅因token更少就认定更好。主体与接收区域的相对关系仍需由原图/深度观测提供。

## 实际任务范围和检测覆盖

当前配置是5个任务ID、10份expert/suboptimal数据，不是10种不同任务。两种示范质量共享相同task_id。

| 任务 | 源位置 | 目标位置 | 需核对的阶段 |
|---|---|---|---|
| unload_dishwasher_to_dresser | 洗碗机 | 抽屉柜 | 源门/架状态、取碗、目的抽屉准备、放置 |
| table_cleanup_to_sink | 桌面 | 洗手池 | 取碗、搬运、定位洗手池放置区 |
| table_cleanup_to_dishwasher | 桌面 | 洗碗机 | 门/架准备、取碗、搬运、放置 |
| table_setup_from_dishwasher | 洗碗机 | 桌面 | 门/架准备、取碗、定位桌面放置区 |
| table_setup_from_dresser | 抽屉柜 | 桌面 | 抽屉准备、取碗、定位桌面放置区 |

这些来自数据集命名和配置，不代表每条示范都必须开关所有门/架。确切操作顺序、是否收尾关闭应逐任务核对示范与环境成功条件，不凭任务名称补造。

现有检测只有红碗、洗碗机门、门把手、碗架、抽屉和抽屉把手。缺少桌面/洗手池放置区域；“抽屉框”也不一定代表安全放碗的区域。需要单独标注/预测目标区域，或在尚无可靠区域时输出无框条件并验证原观测策略的能力。不能把GT场景坐标、固定相机像素或最近检测框当作在线目标区域。

## 从观测到动作的闭环

每次策略query读取截至当前的原始观测和机器人状态，更新对象身份、当前抓持状态、容器状态及阶段，再选择交互目标，最后调用动作策略。动作块结束后重新观察和验证。

```text
任务ID + 当前/短历史观测 + 机器人状态
                    ↓
       估计阶段、抓持状态、容器状态
                    ↓
      按阶段选择目标角色及允许候选
                    ↓
  同类具体实例选择 / 放置区域定位 / 无目标
                    ↓
         身份保持、可见性与不确定性检查
                    ↓
           单个目标条件或无效条件
                    ↓
      扩散策略生成并执行一个动作块
                    ↓
       新观测验证结果 → 保持/切换/恢复
```

任务ID约束目标类型，不能唯一确定当前阶段或同类实例。先验可以缩小候选，但不能直接用最高分对象代替阶段判断。阶段可以跳过已完成的准备步骤，也必须允许重试和退回，不采用固定帧号或固定持续时间切换。

## 以桌面碗放入洗碗机为例

下表是一种门/架未就绪且夹爪未持物时的可能顺序，不硬套到所有任务或所有示范。准备阶段的依赖关系应保证单夹爪可以完成操作。

| 阶段 | 主体/当前单框 | 允许切换的可观测证据 | 失败或不确定时 |
|---|---|---|---|
| 准备门 | 保留将搬运碗的候选身份；当前框为门把手 | 门达到可操作开度的估计有足够证据 | 留在门操作/重定位，不跳到抓碗 |
| 准备碗架（如需） | 当前框为目标碗架/拉动部位 | 接收区域已可接近 | 不以检测到碗架就当准备成功 |
| 接近并抓碗 | 主体锁定某只碗；当前框为该碗 | 夹爪状态、碗与末端的相对运动等支持已抓住 | 抓取未确认则继续定位该碗或重试 |
| 搬运并接近接收区 | 主体仍为同一只碗；当前框可切为碗架放置区域 | 到达可放置位置且碗仍被持有 | 掉碗/持物不确定则进入恢复，不继续假设成功 |
| 放置与释放 | 主体仍记录该碗；当前框为放置区域 | 释放后碗稳定留在目的区域、机器人可撤离 | 区分未释放、掉落、位置偏差，重新观察 |
| 核验与收尾 | 无需对象引导时允许无框 | 满足该任务成功条件；必要收尾另行验证 | 不把动作执行完或夹爪张开当作任务成功 |
```

夹爪闭合不等于抓住物体、二维框重叠不等于到达三维接触位姿。运行时这些是带不确定性的观测估计，不能把仿真GT当成现成传感器。任务完成不能仅凭高层阶段状态声明。

“碗→碗架”的切换只有在进入接收区引导阶段时才合理；若仍在接近/抓取碗阶段，选碗架就是错误。评估必须同时核对阶段、目标角色和具体实例，不能只核对类别/框IoU。

## 单目标条件怎样接入

建议接口包含phase、role、kind（物体/区域/无目标）、instance_id（仅后台身份管理）、当前box、box_valid、visible/age和选择不确定性。只有当前可靠框可作为当前坐标；短暂遮挡可保留身份和历史用于重定位，但不把相机移动前的旧框当当前位置。

动作模型保留原本全部场景观测，额外接收一个目标条件token：

```text
[扩散时间步 token | 目标条件 token | t0观测 token | t1观测 token]
```

目标条件可由box及阶段/角色/有效性编码为一个向量；如实验限定只给四坐标，应把阶段/角色作为选择器内部状态，并明确策略未显式接收它们。两种接口不能混报成同一消融。原图、深度、腕部图像和proprio等原有输入不因单框而丢弃。当前仓库代码仍是8个对象条件token，本接口尚未接入。

无目标、候选角色冲突、框缺失时，目标分支输出无效掩码；不强行塞一个错误框。训练时必须覆盖无框、漏检及错误候选，并检查移除条件后的行为。当前有框训练的模型不能直接宣称具备可靠的无框回退能力。选框网络最大softmax也不是已校准的正确概率；拒选阈值/分数差应在dev调定后冻结。

目标切换遵循两种情况：阶段已由证据确认改变，允许改变交互角色；同一阶段内，仅在原实例丢失或确认选错且新实例证据充分时重新选择。选择分数稍有变化不触发换目标。恢复也应允许解除错误锁定；不能为了稳定而永久锁住错误对象。

## 原型哪里不够

已做原型使用“当前运动对象，否则未来2秒最先运动对象”的代理目标，没有独立的阶段/主体/接收区域监督。它可能在机器人仍操作碗时提前要求选碗架，也可能漏掉无物体运动的失败抓取。仅用5cm几何接近无法确认真实接触意图；未标注区间也不能自动视为无目标。

因此原型的108/130选对，只说明对已有代理标签的框匹配；不能证明整个操作逻辑正确。IoU保持在两轨迹上没有提高结果，已经说明单纯锁框不足以解决阶段切换。

## 应按什么顺序做

1. 对五类任务复核真实示范与成功条件，建立允许跳过/重试的阶段和前置条件；优先标注包含失败、遮挡、切换和导航/无目标的完整episode。
2. 标注阶段、主体实例、当前交互目标及角色、可见性/放置区域、转移证据和不确定区间。仿真状态用于离线辅助标注，人工复核关键边界；不用未来标签生成在线输入。
3. 先跑人工指定正确阶段/单目标框的oracle短程对照。若理想单框也没有收益，不继续扩大选择器训练；oracle只用于诊断上限，不当自动系统结果。
4. 再训练并在独立episode测试自动阶段/目标选择，测接触前错选、提前/延迟切换、错误锁定、拒选、同类实例混淆与目标区域定位。训练/开发/测试按episode隔离，不能因已看过测试失败就继续称其新holdout。
5. 最后接入策略，比较同配方原DP、oracle单目标、自动单目标和屏蔽框对照，报告闭环任务成功率与完整时延，区分感知收益和记忆收益。

原A1/A2/A3实验定义暂不改名：单目标接口是新条件设计。若以后比较单目标版A1/A2/A3，需要三组共用目标选择协议，历史仅来自同一目标实例，不将不同阶段的碗、把手、碗架历史串成一条对象轨迹；任何选择器差异必须作为额外变量记录。
